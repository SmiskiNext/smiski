## Requirements

### Requirement: Database-per-service ownership

Each service SHALL own its Postgres database exclusively and SHALL NOT declare
foreign keys, views, or triggers that reference another service's tables. When a
row must be correlated with an entity owned by another service, the reference
SHALL be stored as a plain identifier column (no cross-database foreign key) so
the two schemas stay decoupled.

#### Scenario: Cross-service correlation without foreign key

- **WHEN** the `record` service stores a recording that relates to a meeting
  owned by the `meet` service
- **THEN** `meeting_id` is a plain `UUID` column with no foreign key to any
  `meetings` table, and the recording can be persisted even though `meet` and
  `record` share no schema

#### Scenario: Intra-service foreign keys allowed

- **WHEN** two tables owned by the same service are related (e.g. `meet`'s
  `invite_tokens` and `meeting_invitees`)
- **THEN** a foreign key MAY be declared between them within that service's
  database

#### Scenario: Reference to a service-owned table is rejected

- **WHEN** a migration attempts to add a foreign key from one service's table to
  a table owned by a different service
- **THEN** the change is rejected in review because it violates
  database-per-service ownership

### Requirement: Multi-tenant hash partitioning

Every business table SHALL be declared `PARTITION BY HASH (tenant_id)` with 16
partitions (`MODULUS 16`, `REMAINDER 0..15`), where `tenant_id` is the Jira
cloudId. `tenant_id` SHALL be the leading column of the table's primary key and
of every unique constraint and foreign key so that per-tenant reads, writes, and
joins prune to a single partition. The `tenants` projection table is the sole
exception and SHALL NOT be partitioned.

#### Scenario: Business table declares 16 hash partitions

- **WHEN** a business table such as `meetings` or `recordings` is created
- **THEN** it is declared `PARTITION BY HASH (tenant_id)` and has partitions
  `_p00` through `_p15`, each `FOR VALUES WITH (MODULUS 16, REMAINDER n)`

#### Scenario: Tenant-leading composite key enables pruning

- **WHEN** a query filters a business table by a single `tenant_id`
- **THEN** the planner prunes to exactly one partition because `tenant_id` is
  the leading key column

#### Scenario: Foreign key carries tenant_id as leading column

- **WHEN** a partitioned child table references a partitioned parent (e.g.
  `participation_logs` → `meetings`)
- **THEN** the foreign key is `(tenant_id, <id>)` referencing `(tenant_id, id)`,
  keeping the join within one partition

#### Scenario: Projection table stays unpartitioned

- **WHEN** the `tenants` read-model table is created
- **THEN** it is a plain, non-partitioned table with `PRIMARY KEY (tenant_id)`

### Requirement: UUIDv7 identifier and composite key convention

Surrogate identifiers SHALL be time-ordered UUIDv7 values generated by the
database default `uuidv7()` (or the application's UUIDv7 factory). Business
tables SHALL use a composite `PRIMARY KEY (tenant_id, id)`. No table SHALL rely
on a global monotonic sequence (e.g. `BIGSERIAL`) for its primary identity.
Secret material such as invite tokens SHALL be stored only as a hash, never in
plaintext.

#### Scenario: Business row gets a UUIDv7 id by default

- **WHEN** a row is inserted into a business table without an explicit `id`
- **THEN** the `id` column defaults to `uuidv7()` and the row is uniquely
  identified by `(tenant_id, id)`

#### Scenario: Natural-key table uses a non-UUID primary key

- **WHEN** the `tenants` table is created and keyed by the Jira cloudId
- **THEN** its primary key is `(tenant_id)` (a `VARCHAR`), not a generated UUID

#### Scenario: Token stored as hash only

- **WHEN** an invite token is persisted in `invite_tokens`
- **THEN** only `token_hash` is stored and the raw token never appears in any
  column

### Requirement: Soft-delete and retention lifecycle

Tables that hold user-facing content SHALL support soft deletion via
`deleted_at` (nullable `TIMESTAMPTZ`) and `deleted_by` (Jira accountId), and a
retention deadline via `purge_after`. Indexes serving live queries SHALL be
partial indexes with `WHERE deleted_at IS NULL` so soft-deleted rows are
excluded, and purge-scan indexes SHALL target `WHERE deleted_at IS NOT NULL`.

#### Scenario: Soft delete hides row from live queries

- **WHEN** a meeting is soft-deleted by setting `deleted_at`
- **THEN** it no longer appears in results served by the live partial indexes
  (e.g. `idx_meetings_status ... WHERE deleted_at IS NULL`)

#### Scenario: Unique constraint ignores soft-deleted rows

- **WHEN** a meeting with a given `short_code` is soft-deleted and a new meeting
  reuses that `short_code`
- **THEN** insertion succeeds because the uniqueness index is
  `WHERE deleted_at IS NULL`

#### Scenario: Purge deadline drives retention scan

- **WHEN** the retention job scans for expired rows
- **THEN** it uses the purge index defined `WHERE deleted_at IS NOT NULL` and
  selects rows whose `purge_after` is in the past

### Requirement: Tenant read-model projection

Every service other than `tenant` SHALL maintain a local `tenants` projection
table synchronised from the tenant service over Kafka. The projection SHALL be
small (one row per site), non-partitioned, keyed by `tenant_id`, and SHALL carry
tenant lifecycle status (`ACTIVE`, `SUSPENDED`, `UNINSTALLED`). Business tables
MAY reference this projection so a tenant is known to exist before any dependent
row is written.

#### Scenario: Projection updated from tenant lifecycle event

- **WHEN** the tenant service emits a tenant status change over Kafka
- **THEN** the consuming service upserts the corresponding row in its local
  `tenants` projection

#### Scenario: Business write requires known tenant

- **WHEN** a meeting is inserted for a `tenant_id`
- **THEN** the `fk_meetings_tenant` foreign key requires a matching row in the
  local `tenants` projection, otherwise the insert fails

#### Scenario: Projection is authoritative source of tenant service

- **WHEN** the tenant service itself stores an installation
- **THEN** it writes to its own `tenants` table (keyed by cloudId with
  installation metadata), which is the source projected to other services

### Requirement: Transactional outbox

Every service that publishes domain events SHALL persist them to an
`outbox_event` table within the same transaction as the state change. The table
SHALL use a tenant-scoped `PRIMARY KEY (tenant_id, id)` with a UUIDv7 `id`,
carry `aggregate_id`, `aggregate_type`, `event_type`, `topic`, and `payload`,
track `published_at`, `retry_count`, and `last_error`, and expose a partial
index on unpublished rows (`WHERE published_at IS NULL`) for the poller.

#### Scenario: Event written atomically with state change

- **WHEN** an aggregate is modified and registers a publishable event
- **THEN** a row is inserted into `outbox_event` in the same transaction, so the
  event is durable if and only if the state change commits

#### Scenario: Poller selects only unpublished events

- **WHEN** the outbox poller scans for work
- **THEN** it uses `idx_outbox_event_unpublished ... WHERE published_at IS NULL`
  ordered by `created_at`, and marks rows by setting `published_at`

#### Scenario: Delivery failure is retryable

- **WHEN** publishing an outbox row to Kafka fails
- **THEN** `retry_count` is incremented and `last_error` is recorded while
  `published_at` remains null so the row is retried

### Requirement: Flyway migration governance

Schema SHALL live under each service's `src/main/resources/db/migration/`. A
clean database SHALL be initialised from a single baseline
`B1.0.0__baseline.sql` (Flyway `B` prefix). All subsequent changes SHALL be
additive `V<n>__<description>.sql` migrations. Applied migrations SHALL NOT be
edited. Runtime SHALL run Flyway with `ddl-auto: validate` (main) / `none`
(test) so JPA `*JpaEntity` mappings must match the migrated schema exactly.

#### Scenario: Clean database initialised from baseline

- **WHEN** a service starts against an empty database
- **THEN** Flyway applies `B1.0.0__baseline.sql` to create the full schema

#### Scenario: Incremental change adds a versioned migration

- **WHEN** a schema change is required after baseline
- **THEN** a new `V<n>__<description>.sql` file is added and the existing
  baseline is left untouched

#### Scenario: Editing an applied migration is rejected

- **WHEN** a developer modifies an already-applied migration file
- **THEN** Flyway's checksum validation fails on startup and the change is
  rejected

#### Scenario: Entity drift fails validation

- **WHEN** a `*JpaEntity` mapping diverges from the migrated schema
- **THEN** startup fails under `ddl-auto: validate` because the entity no longer
  matches the table
